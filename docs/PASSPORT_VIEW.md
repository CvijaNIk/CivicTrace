# Synthetic Evidence Passport finding view

The opt-in `/?view=passport` page extends the existing React application. It does
not replace the record explorers or introduce another Parquet adapter. It consumes
only a compiled, reviewed synthetic example generated by
[scripts/export_passport_view.py](../scripts/export_passport_view.py).

## Reproduce

```sh
python -m pip install -e '.[dev]'
python scripts/export_passport_view.py --check
python -m pytest -q
cd frontend
npm ci
npm run build
npm test
npm run format:check
npx playwright install --with-deps chromium
npm run test:browser
npm run dev
```

Open the loopback URL with `/?view=passport`. Expect four open articles: one 0.1.0
finding, its 0.2.0 incomplete migration, and two 0.2.0 complete synthetic findings.
The first three intentionally share one finding identity: these are compatibility
examples, not three independent observations. Both original record views remain
available through navigation. `analytics_enabled: false` remains mandatory.

The generator calls the existing `single_bid_findings`, `fixture_passports`,
`verify_fixture_passports` and `migrate_passport` implementations. It checks both
frozen JSON schemas using date-time format validation. It never accepts an external
file or real-source input. Regeneration without `--check` replaces only the compiled
example, for review. CI and pytest compare every field except the verification-time
environment, which differs across hosts. That environment is displayed as recorded,
not reconstructed or presented as the historical acquisition environment.

## Presentation and trust

`PassportFinding` validates unknown props against the frozen 0.1.0/0.2.0 schemas
using Ajv 2020 plus formats. Extra consistency checks reject conflicting original
hashes/timestamps, duplicate artifact IDs and unresolved transformation references.
This checks structure and internal references; it does **not** rehash source bytes,
replay computation, authenticate a publisher or certify a finding. Existing backend
replay remains the evidence check. The view never upgrades a metadata status into a
verification result. Synthetic flags and the component's synthetic guard are not
proof of origin; review the compiled fixture and its independently pinned source.

Display order follows [EVIDENCE_PASSPORT.md](EVIDENCE_PASSPORT.md): identity, source,
methodology, source-reported facts, computation, benchmark, limitations/uncertainty,
derived interpretation, unverified allegations and required verification steps.
Lineage then exposes original/expanded and artifact/implementation SHA-256 values,
source pointer, operation versions, input/output references, rights, environment and
lineage limitations. Arrays retain evidence order; object keys sort deterministically.
The component does not recompute amounts or infer absent facts. Null/absent supported
metadata stays “Unknown — not supplied”; empty arrays say “None supplied”. Zero
remains zero. No real-world facts are claimed independently confirmed. Allegations
and interpretations have separate explicit headings. No arbitrary probability is added.

Legacy missing expanded hashes, transformations and historical environment are
explicitly unknown. A migrated `legacy-incomplete` passport has an additional visible
warning. Required metadata missing from a malformed passport rejects that whole
article with a generic accessible alert; it does not show a partially trusted finding.

Every source-provided string, including object keys and artifact names, is a React
text node. There is no raw HTML, Markdown renderer, dynamic CSS, source-defined DOM
ID, executable formula or file-path navigation. Only absolute HTTP/HTTPS references
without whitespace, controls, backslashes or credentials become links. Other references
remain inert text, including local URNs and `javascript:`, `data:`, `file:` and relative
URLs. Links suppress referrers. This scheme policy does not certify destination safety;
no link is automatically fetched or embedded.

Limitations, uncertainty and rights are always expanded in normal document flow.
Semantic articles/headings, generated unique heading IDs, keyboard skip navigation,
wrapping long tokens and visible focus inherit the existing application styles.
No excerpt, collapse, pagination or ellipsis hides evidence. Per-article ceilings:
16 nesting levels, 10,000 visited JSON nodes, 256 array entries, 256-character keys
and 16,384-character values. Exceeding a ceiling rejects the article, never truncates
it. Only safe-integer JS numbers are accepted; precise financial decimals must be
strings, preserving all digits. This intentionally narrower display boundary is not
a general arbitrary JSON viewer. There are no new fetch endpoints, uploads, browser
filesystem access, arbitrary queries, real analytical indicators or public findings.

## Validation coverage

Frontend tests exercise both frozen versions, incomplete migration, exact decimals,
null/zero, stable rendering, inert HTML/JavaScript, URL scheme/credential/control
rejection, allowed HTTP(S), long limitations, unique headings, missing required fields,
invalid source/hash/date, conflicting lineage, disabled analytics and resource ceilings.
Python tests regenerate and replay the existing invented evidence and check lossless
migration and compiled-example semantics. The browser scenario checks all four
articles, keyboard navigation, axe WCAG A/AA rules and a 375px viewport. Actual
execution results and any environment limitations are recorded in the draft PR.

This implements the synthetic safe-presentation portion of #17 only. Real-source
rights, privacy, production cohort semantics and source authentication remain open.
